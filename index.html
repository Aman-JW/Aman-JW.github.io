Employee compliance workflow

Rolling out

Event-driven violation handling: automated detection, human review, manager acknowledgement, one auditable record.
  1. Detect
  2. Record evidence
  3. Officer review
  4. Notify manager
  5. Sync response

Problem

Violation signals arrived from scheduled detectors and from officers by hand. There was no system of record, no review gate before people were notified, and no audit trail of manager responses.

What I built

  • Defined the finding schema and status lifecycle, scoped to employee-level violations.
  • Orchestrated five n8n workflows: slash-command intake, review API, manager reporting, acknowledgement sync and officer directory sync.
  • Built the Appsmith review console on a REST review API, with no direct database access.

Controls

  • L1 to L2 escalation driven by per-rule thresholds and time windows stored in Strapi.
  • Self-approval blocked; approver-based routing; unresolved findings carry forward.
  • Acknowledgement needs a form submit, so email link scanners can’t trigger it.
Role Lead contributor   Stack n8n, Appsmith, ClickHouse, Airflow, Strapi, Mattermost, Redmine, SQL

Policy-as-code tool audits

Rolling out

Versioned, scheduled checks that compare internal tools against written standards and store every finding.
  1. Python checks
  2. GitHub
  3. Airflow DAGs
  4. ClickHouse
  5. Superset

Problem

Configuration standards for n8n, Strapi, TwentyCRM and Twilio lived only in documents, so drift went unnoticed until something broke.

What I built

  • Translated written standards into Python checks against each tool’s admin API.
  • Versioned the checks in GitHub and scheduled them as Airflow DAGs.
  • Wrote a shared writer that persists findings to ClickHouse, exposed as Superset datasets.

What I learned

Re-runs created duplicate findings. Deterministic finding IDs (tool, rule, object) let the pipeline upsert instead of append, with separate open and resolved views people can actually close out.

Role Workstream owner   Stack Python, GitHub, Apache Airflow, ClickHouse, Apache Superset, REST APIs

Outbound pipeline & deliverability

From public SEC filings to scored, CRM-ready leads, sent from authenticated domains.
  1. 13F / ADV filings
  2. Enrichment
  3. Sequenced email
  4. Lead scoring
  5. CRM handoff

Problem

Sales needed repeatable outreach to investment firms without putting the company’s primary domain reputation at risk.

What I built

CRM migration & audited merges

Rolling out

Relational data model, hygiene rules and API integrations for a GoHighLevel to TwentyCRM move.

Problem

The legacy CRM couldn’t model relationships between people, companies and deals, and the new CRM’s native merge could orphan notes and linked records.

What I built

  • Mapped legacy fields to TwentyCRM objects (People, Company, Opportunity, Activity), preserving source IDs for reconciliation.
  • Wrote hygiene standards: required fields, dedupe keys, same-day activity logging.
  • Built n8n webhook integrations into the TwentyCRM REST API, resolving redirect and enum-validation failures.

Audited merge design

Pre-merge snapshots, a confidence-tiered candidate queue, human approval and rollback, so no merge destroys data silently. Currently at roadmap stage.

Role Contributor, data & integrations   Stack TwentyCRM, GoHighLevel, PostgreSQL, n8n, REST, webhooks

Company data layer

Designed

A medallion-architecture warehouse to replace spreadsheet-driven reporting.
  1. Sources
  2. Bronze
  3. Silver
  4. Gold
  5. BI & AI agents

Problem

Data lived across Baserow, spreadsheets, SharePoint and several CRMs, so every report began with copy and paste.

What I did

  • Wrote pipeline requirements: key mapping, idempotent upserts, incremental sync, retries and dead-letter handling.
  • Built the ER model that standardised core entities.
  • Evolved the design from Baserow and PostgreSQL to ClickHouse Bronze, Silver and Gold layers with Airflow, NiFi and dbt.

Scope

A cross-functional build. A partner DevOps team owns platform infrastructure; I own requirements, data modelling and application-level work.

Role Project owner, architecture   Stack ClickHouse, PostgreSQL, Baserow, Airflow, NiFi, dbt, Superset

Joiner–leaver identity automation

Designed

One identity record that provisions and de-provisions accounts across six systems.

Problem

Accounts were created by hand in each tool, so usernames drifted and leavers sometimes kept access.

What I built

  • Specified Entra ID as the authentication source of truth and Baserow as provisioning state, with a per-tool external-ID map.
  • Prototyped idempotent onboarding in n8n with JSON-schema validation and a credentials pre-flight check.

Safety rules

Approval gates on privileged steps, no stored passwords in automation, disable-not-delete on offboarding, and a reconciliation job to catch drift.

Role Solution designer   Stack Microsoft Entra ID, Microsoft Graph, n8n, Baserow, Redmine, Mattermost APIs
